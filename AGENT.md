# AGENT.md

This file provides guidance to Coding Agents when working with code in this repository.

## Project Overview

Atakora is a type-safe Infrastructure as Code (IaC) framework for Azure that combines the flexibility of ARM templates with the power of TypeScript. It synthesizes TypeScript constructs into Azure Resource Manager (ARM) templates for deployment.

**Key Concept**: Atakora is NOT a runtime framework - it's a build-time code generator that produces ARM JSON templates. The TypeScript code you write is transformed into static ARM templates during synthesis.

## Repository Structure

This is a TypeScript monorepo with npm workspaces containing 5 main packages:

- **@atakora/lib** - Core framework with synthesis engine, validation, and authorization abstractions
- **@atakora/cdk** - L1/L2 Azure resource constructs organized by Microsoft.* namespaces (Network, Storage, Compute, etc.)
- **@atakora/cli** - Command-line interface for project initialization and deployment
- **@atakora/component** - Production-ready infrastructure patterns (CRUD APIs, web apps, microservices)
- **@atakora/backend** (private) - Example/internal backend infrastructure package

## Architecture Patterns

### Construct Tree Model

Atakora follows AWS CDK's construct tree pattern with three levels:

1. **App** (root) - Entry point, orchestrates synthesis, loads configuration
2. **Stack** - Deployment boundary (ResourceGroupStack or SubscriptionStack)
3. **Resources** - Azure resources (L1 low-level, L2 high-level intent-based)

Example hierarchy:
```
App
└── ResourceGroupStack (Foundation)
    ├── VirtualNetworks (L2 construct)
    │   └── ArmVirtualNetwork (L1 construct) → ARM template
    ├── StorageAccounts (L2 construct)
    │   └── ArmStorageAccount (L1 construct) → ARM template
    └── DatabaseAccounts (L2 construct)
        └── ArmDatabaseAccount (L1 construct) → ARM template
```

### Synthesis Pipeline

The synthesis process transforms the construct tree into deployable ARM templates:

1. **Preparation** - Walk construct tree, collect resources
2. **Context Resolution** - Resolve resource dependencies and references
3. **Transform** - Convert constructs to ARM JSON resources
4. **Assembly** - Generate linked templates, function packages, storage artifacts
5. **Output** - Write templates to `arm.out/` directory

**Critical**: Synthesis is async (`app.synth()` returns a Promise) due to bundling and artifact processing.

### Linked Templates Strategy (ADR-017)

Atakora uses linked templates as the default and only synthesis approach:

- **Why**: ARM templates have a 4MB size limit; embedding function code hits this limit with just 2-3 CRUD APIs
- **How**: Main template references child templates stored in Azure Blob Storage
- **Function Deployment**: Uses "run from package" pattern with Storage for function code
- **Developer Impact**: None - existing code works unchanged, complexity is hidden in synthesis

### Type System

The framework has two distinct type systems:

1. **Schema Types** (`@atakora/lib/schema/*`) - Generated from ARM JSON schemas
   - Exact representations of ARM API contracts
   - Used for validation and L1 constructs
   - Generated by codegen tools (see packages/lib/src/codegen)

2. **CDK Types** (`@atakora/cdk/*`) - Handwritten TypeScript constructs
   - Intent-based, developer-friendly APIs
   - L2 constructs that generate L1 constructs
   - Should import from `@atakora/lib` for core types

**Import Pattern**: CDK constructs must use:
```typescript
import { Construct, Resource, DeploymentScope } from '@atakora/cdk';
import type { ArmResource } from '@atakora/cdk';
```

### Backend Component Pattern (ADR-018)

The `@atakora/component` package provides a resource pooling system for building backends:

- **Resource Providers**: Cosmos, Functions, Storage providers manage shared resources
- **Components**: Declare requirements, backend provisions and injects resources
- **CRUD Factory**: `createCrudBackend()` bundles multiple CRUD APIs
- **Smart Sharing**: Resources are shared when possible, split when necessary

Current implementation (~2500 lines) is sophisticated. File-based definition improvements are planned incrementally.

## Code Generation

Atakora includes codegen tools for ARM schema processing (see docs/contributing/technical/codegen.md):

```bash
# Generate TypeScript types from ARM schema
npm run codegen:types <schema-path> [output-path]

# Generate L1 construct from ARM schema
npm run codegen:resource <schema-path> <resource-index> [output-dir]

# Generate validation logic
npm run codegen:validate <schema-path> [output-path]

# Sync all schemas (automated daily via GitHub Actions)
npm run codegen:sync [schemas-dir] [pattern...]
```

Generated code locations:
- Types: `packages/lib/src/generated/types/`
- Validation: `packages/lib/src/generated/validation/`
- Resources: `packages/lib/src/resources/<namespace>/`

## Package Dependencies

Internal dependency order (build order):

1. `@atakora/lib` (no internal deps)
2. `@atakora/cdk` (depends on lib)
3. `@atakora/component` (depends on lib + cdk)
4. `@atakora/cli` (depends on lib + cdk, bundled with esbuild)
5. `@atakora/backend` (depends on lib + cdk + component)

**Important**:
- CLI is bundled into a single file (`dist/cli.bundle.js`) using esbuild
- Lib and CDK must build before CLI
- Use `npm run build` from root to build in correct order

## Common Patterns

### Creating a New Resource Construct

1. Find ARM schema in Azure ARM schemas repository
2. Generate L1 construct: `npm run codegen:resource <schema> <index>`
3. Create `types.ts` with enums and helper types
4. Build L2 construct with developer-friendly API
5. Add tests with >80% coverage
6. Export from `packages/cdk/src/<namespace>/index.ts`

### Working with Function Apps

Function Apps have two storage requirements:

1. **Runtime Storage** - Required by Azure Functions (auto-provisioned)
2. **Application Storage** - Optional, for application data

Per ADR-001, these must be separate storage accounts for proper isolation.

### Resource Naming

Use `@atakora/lib/naming` utilities for Azure naming conventions:

```typescript
import { AzureNaming } from '@atakora/lib/naming';

const storageName = AzureNaming.storageAccount('myapp', 'prod');
// Returns: stmyappprod (lowercase, no hyphens, 3-24 chars)
```

## Development Guidelines

### TypeScript Configuration

- Uses TypeScript 5.9+ with strict mode
- Target: ES2020
- Module: CommonJS (for Node compatibility)
- Path aliases configured in `tsconfig.base.json`

### Code Style

- ESLint with TypeScript rules
- Prettier for formatting
- Husky pre-commit hooks run linting and formatting
- Max warnings: 0 (CI fails on warnings)

### Commit Messages

No specific convention enforced, but be descriptive. Commits include:
- What changed and why
- Reference ADRs for architectural decisions

### Branch Strategy

- Main branch: `main`
- Current working branch: `backend`
- Feature branches: Use descriptive names

## Key Architecture Decisions (ADRs)

Important ADRs to review when working on related features:

- **ADR-001**: Functions storage separation (runtime vs application storage)
- **ADR-017**: Linked templates as default (solves 4MB ARM template limit)
- **ADR-018**: Backend API redesign assessment (incremental improvements planned)
- **ADR-019**: Synthesis pipeline refactoring

ADRs are located in: `docs/architecture/decisions/`

## Troubleshooting

### Build Issues

```bash
# Clean and rebuild everything
npm run clean
npm install
npm run build
```

### Type Errors in CDK

Ensure you're importing from the correct package:
```typescript
// Correct
import { Construct, Resource } from '@atakora/cdk';

// Incorrect (old pattern)
import { Construct, Resource } from '@atakora/lib';
```

### Synthesis Failures

Check the `arm.out/` directory for:
- `manifest.json` - Synthesis output manifest
- `<stack-name>.template.json` - Main ARM template
- `<stack-name>-*.template.json` - Linked templates
- `functions/` - Function code packages

### Test Failures

```bash
# Run tests in watch mode to see detailed output
npm test -- --watch

# Run specific test file
npm test -- packages/lib/src/core/app.test.ts

# Run with coverage to see uncovered lines
npm test -- --coverage
```
